# 自分析示例：用本 Skill 分析它自己的仓库

这份文档是把 Git Resume Analyzer 用在本仓库（git-resume-analyzer）上的产出，
作为「采集 → 分析 → 成文」整条链路的展示样例。

- 数据来源：本仓库 git 历史（作者 uuicdown，3 次提交，+1,745 / -114 行，8 个文件）
- 采集方式：`python git_resume_analyzer.py --author uuicdown --json --no-merges`
- 分析方式：AI 基于采集数据，读脚本与文档，按 `GIT-RESUME-SKILL.md` 的模板成文

---

## 简历（技术 + 问题 + 功能）

**Git Resume Analyzer**（用 AI 从 git 历史产出简历的 Skill，2026-06 ~ 2026-09）

- 用"Python 采集脚本 + Markdown 规则手册"组合成一个 AI Skill：脚本跑 `git log` 导出结构化提交数据，规则手册指导 AI 结合 diff 与源码推断问题、技术栈与实现方式，解决 git 历史难以直接变成简历素材的问题，实现一条从仓库到简历/讲稿的可复用流程。
- 用 `subprocess` 调 `git log` 的 `%h/%ai/%s/%B` 加 `--numstat`，采集每个提交的哈希、时间、标题、正文、文件列表和增删行数，输出 JSON 或文本摘要供 AI 消费。
- 用不可打印字符（`\x1f`/`\x1e`）分隔字段与记录、把元数据和 numstat 拆成两条命令采集、用父提交数（`%P`）判断 merge，解决提交正文含换行或 `|` 时记录被撕裂、文件统计被污染、合并提交漏判的问题。
- 用可重复传参的 `--author` 合并同一人的多个 git 身份，解决同一人用不同身份提交、产出被拆分统计的问题。
- 用标准库 `unittest` 建一次性 git 仓库做回归测试，覆盖上述解析场景，并做受限环境的临时目录可写回退，保证测试可重复运行。

技术栈：Python、Git、Markdown（Agent Skill 规范）

## 讲稿（讲自实现）

我做的是一个 AI 技能，把一个人的 git 提交历史变成能写进简历的内容。

设计上是两段分工。Python 脚本只做机械采集——用 `subprocess` 跑 `git log`，按 `%h`、`%ai`、`%s`、`%B` 取出每个提交的哈希、时间、标题、正文，再用 `--numstat` 拿文件列表和增删行数，拼成结构化 JSON 交给 AI。规则手册写成 Markdown，指导 AI 从这些数据、加上 diff 和源码，推断每个提交解决了什么问题、用了什么技术、怎么实现的，再按模板成文。

采集踩过几个坑，都修了。原来用 `|` 当字段分隔符，正文里出现 `|` 就把记录切断；换成不可打印的 `\x1f`/`\x1e`，并把元数据和 `--numstat` 拆成两条命令取，正文再长也不污染统计。merge 判断原来只看标题是不是以 "Merge" 开头，rebase 或中文标题就漏，改成看父提交个数。后来加了多作者：`--author` 可以传多次，一次合并同一人的多个身份。

为防回退，我写了标准库 `unittest` 的测试，在临时 git 仓库里造出这些场景断言解析正确，并处理了受限环境里 `mkdtemp` 目录写不进文件的回退。

## 这个样例说明了什么

1. **自举可行**：skill 能分析包括它自己在内的任意 git 仓库，不需为自身做特殊处理。
2. **分工生效**：脚本只出数据，语义判断（这篇简历里的"解决什么问题、用了什么技术"）全部由 AI 读源码得出。
3. **可复现**：上面的数据用一条命令即可重新得到，结论随之可核对。
